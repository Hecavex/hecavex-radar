# Architecture

This document describes the production architecture behind the HECAVEX-operated service at [radar.hecavex.com](https://radar.hecavex.com). Radar uses a Python collection and validation pipeline with a static React/TypeScript viewer; it is not a reusable application architecture or self-hosting guide.

| Input | Gate before publication | Public label |
| --- | --- | --- |
| CertStream certificate names and bounded leaf metadata | Current Lithuanian brand matcher, confidence threshold, certificate-field allowlist, and daily archive validation | `CertStream` |
| `crt.sh` indexed results for reviewed brand keywords | Per-query result checkpoint, seven-day bounded bootstrap, row cap, shared brand matcher, and CT archive validation | `CertStream`; `discoveredVia` identifies `ct-search-api` |
| Existing URLScan reports | Passive searches, automated same-brand evidence checks, official-domain suppression, and report validation | `URLScan` |
| DNS-over-HTTPS and RDAP for current published candidates | Current-snapshot membership, exact allowlists, defanging, byte/record limits, and 14-day expiry | Context only; never a signal source |
| Configured HECAVEX public export | HTTPS fetch, public schema validation, and shared brand/safety checks | `HECAVEX` |
| Explicit sanitized local review export | Private append-only ledger, intentional bounded export, current matcher, and public schema checks | `HECAVEX`; `discoveredVia` identifies `hecavex-review` |
| Transient intelligence seeds | Exact URLScan lookup only; seeds are neither archived nor published | None |

## Runtime

Live CertStream, checkpointed CT search, and URLScan collection write bounded repository archives. Every live CertStream workflow attempt also atomically replaces one bounded `public/data/collection-health.json` document with actual attempt timing and aggregate counts; it never contains certificate names or unpublished candidates. Because that latest-attempt document advances independently four times per hour, it is outside the hourly release manifest and checksum set. The synchronized `pipeline-health.json` carries its bounded release-time aggregate instead. The hourly `crt.sh` poller persists a result-ID checkpoint independently for each selected brand query and writes qualifying matches through the same CT candidate archive as the live listener. `python -m hecavex_radar.sync` validates the archives together with optional HECAVEX and sanitized review inputs, then merges, limits, and sorts one accepted signal set. That set produces the defanged `public/data/radar.json` dashboard snapshot, deterministic complete-set shards, the observation-only `public/data/radar.stix.json` STIX 2.1 projection, and the separate analyst-reviewed `public/data/radar-reviewed.stix.json` Indicator projection. Synchronization also writes bounded per-signal detail sidecars, 24-hour/seven-day health and change aggregates, typed related-observation associations, versioned schemas, checksums, and one release manifest. A qualifying CT observation becomes a `suspected` dashboard row even when URLScan has no report; URLScan can add a report, screenshot, hashes, and hosting metadata later but is never a publication gate for that row.

The credential-free domain-context job runs four times per day against the current published signal list. It performs only DNS-over-HTTPS questions and IANA-bootstrapped RDAP registration lookups, never a request to the candidate webpage. RDAP is scoped to the registrable parent and that defanged scope is published with the limited registrar, lifecycle timestamp, and status-code allowlists. Synchronization discards records older than 14 days, attaches current rows to optional signal-detail sidecars, exposes aggregate job health, and may use DNS values as bounded non-attribution relation evidence.

URLScan is an optional passive enricher scheduled at minute 37 every two hours. Each search is limited to existing public reports from the rolling previous seven days. Every run attempts the complete bounded set of at most 250 recent CertStream, Radar-snapshot, and transient discovery candidates. A deterministic cursor preserves progress when an operator lowers the per-run selection or a request budget interrupts that set. Result retrieval remains passive: Radar neither submits a scan nor visits a candidate host.

Each material hunter state transition atomically replaces `data/urlscan/hunt-state.json`, and the workflow stages `data/urlscan/` even when the hunter ultimately reports failure. The fixed, bounded ledger contains only configuration state, UTC budget counters, a numeric cursor, candidate counts, timestamps, and an outcome; it contains no API key or candidate domain. If the credential is absent, the hunter makes no API request, records `configured: false` and `skipped-not-configured`, and exits successfully. Repeated identical unconfigured runs in the same UTC day remain visible in Actions history but do not rewrite the timestamp-only ledger or create empty commits. A failed or rate-limited refresh remains observable without removing, treating as benign, or downgrading an independently qualifying CertStream candidate.

The CT-search and domain-context jobs follow the same observable-failure pattern: each writes its bounded latest-run state before the workflow propagates a failed job result, and the commit step stages that state even after the collector step fails. This records ordinary request and parser failures while preserving a red workflow result. It cannot record a hard runner cancellation, an outage before checkout, or state that never reaches the repository after all push retries.

Synchronization also assigns deterministic event IDs to accepted observations and explicit status changes. Daily history partitions are append-only inside a 30-day default detail window. Older partitions compact into a bounded two-year summary; the public projection is `public/data/history.json`. Absence from a later source window does not generate a transition. Each output file is replaced through a temporary file, while one Git commit is the atomic public-data transaction for the snapshot, STIX projections, shards, sidecars, aggregates, schemas, digests, manifest, and history artifacts.

Private review is a separate trust boundary. `hecavex-review` keeps an append-only SQLite ledger outside the repository. An operator must explicitly export active decisions into `data/review/public-decisions.json`; only that strict, defanged schema is consumed by synchronization. A time-bounded positive assessment, correction, expiry, or retraction is therefore distinct from automated matching and provider evidence. Private notes, analyst identity, and raw evidence never cross the export boundary.

Pages builds the committed dashboard together with reader-facing `/history/`, `/methodology/`, and `/docs/` pages and copies the public JSON distributions unchanged. The browser has no application backend, login, or database. The STIX file is a static HTTPS pull/download, not a TAXII discovery or Collections service. The core snapshot declares only whether a detail sidecar exists; the browser requests that same-origin static file only when a reader opens evidence for the row. A centrally injected, Do Not Track-aware Cloudflare Web Analytics loader provides cookieless page-view and browser-performance measurement; it is separate from the CTI pipeline and receives no custom events, signal rows, search text, filter values, or unpublished candidates. HECAVEX feed URLs require HTTPS in production and cannot contain credentials or an explicit port. HTTP is accepted on `localhost`, `127.0.0.1`, or `::1` at the default port only for local maintainer validation.

## Certificate Transparency coverage

The live GitHub Actions listener is scheduled for eight minutes four times per hour. That is at most 768 minutes, or 53.3% of a day, only when every run starts and completes. It is a low-latency sampled input, not continuous coverage. The public health file makes late, empty, partial, and failed sampled windows visible; it does not recover dropped schedules or events outside a listening window.

The hourly `crt.sh` path adds bounded replay for reviewed brand keywords. It rotates through six queries per run by default, reads no more than 500 result rows per query, and limits a new query to a seven-day bootstrap. Its persisted per-query result ID resumes that selected search after ordinary downtime, while a default 50-row/1,000-ID overlap rechecks a bounded slice for late-indexed records. A backlog is marked partial and resumed before rotation. These are provider-index cursors, not RFC 9162 log positions: the path neither proves which logs are complete nor discovers certificates whose names do not match a reviewed query. [ADR 0001](decisions/0001-ct-coverage.md) records why Radar continues to reject complete daily or global CT coverage claims.

## Safety boundaries

- All certificates, reports, archives, seeds, and configured exports are untrusted input and are normalized and validated before use.
- Certificate and result details use exact schemas, per-file and aggregate byte caps, same-host/same-registrable checks, and indicator defanging before publication. A sidecar never adds a source or candidate that is absent from the live snapshot.
- Collection is passive. CertStream supplies live certificate names, `crt.sh` supplies indexed CT search results, URLScan supplies existing reports, and DNS/RDAP supply point-in-time infrastructure context. Radar does not visit candidate webpages or submit URLs for scanning.
- DNS/RDAP context is collected only for current published candidates, expires after 14 days by default, and excludes registrant PII and raw responses. Shared DNS or registration context is neither a verdict nor attribution.
- URLScan request budgets default to 25 searches and 100 result retrievals per run, and 900 searches and 8,000 result retrievals per UTC day. These conservative local limits remain below the published provider quotas. Only successful responses increment the local ledger; HTTP 429 stops the run without further requests.
- Dashboard, history, archive, and detail indicators remain defanged text. The STIX projection is the deliberate exception: standard `domain-name` SCO values are normalized and refanged for interoperability, while URL paths and other unsafe fields are omitted. Its optional external reference is emitted only for a canonical URLScan result URL. Screenshots use HTTPS on exactly `urlscan.io`—never a subdomain—and contain no credentials, explicit port, query string, or fragment. Published hashes are SHA-256 values for the primary HTML document.
- Only the sync stage writes the public snapshot. Publication is guarded against invalid or unexpectedly small output, and one unavailable optional source does not erase healthy-source data. The 512 KiB dashboard is a proven newest-first prefix; the complete accepted set is preserved in independently hashed 256 KiB shards.
- History event identity excludes mutable scoring explanations, so a registry wording or score change cannot turn one source observation into multiple events. Brand conflicts are rejected before history publication.
- An operator review addition must independently pass the current public domain matcher. Its `matchScore` cannot exceed that matcher, its status is always `suspected`, and a suppression takes precedence over an addition. Only a separately exported, expiring analyst confirmation can set `confirmed-suspicious` or produce a STIX Indicator.
- Collection health uses a strict fixed-field schema, a 32 KiB limit, and atomic replacement of one file. It exposes aggregate counters and timing only, so attempts do not create an unbounded telemetry archive.
- HECAVEX integration accepts a deliberately limited public export. Private detector features, working graphs, analyst notes, user data, credentials, and internal history stay outside this repository. The public relation graph uses only bounded typed evidence already present in public rows/sidecars, suppresses high-fanout values, and states association without attribution.
- Cloudflare Web Analytics is restricted by CSP to its exact hosted beacon and reporting origin. The loader stops when `navigator.doNotTrack` or `window.doNotTrack` is `1`; otherwise the beacon uses no cookies or browser storage, and Radar does not connect CTI interactions to custom analytics events.
